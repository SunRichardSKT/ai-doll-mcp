# Operit 原型验证记录

日期：2026-10-14。原型 0.1.0，基于 Bridge 2.18.0，不重刷固件或修改电气参数。

## 已完成

- 旧 Operit 查询包补齐六个自然陪伴工具，支持现有 19 工具。
- 独立 Workflow 列出并绑定已有聊天，有限会话每次读取最多等待 20 秒。
- 新压力来源、部位等级、质量、期限、静音／关闭状态由服务器上下文和本机检查共同限制；释放、旧事件、输出和故障不发主要回复。
- 发送前保存恢复状态，发送成功后确认服务器上下文；不明确的结果阻止自动重发，ACK 失败只补确认。
- 电脑局域网启动入口及隔离的模拟演示，不需要公网隧道、域名、远程服务器或开发板。

## 检查方法

`node tools/test_operit_package.cjs` 验证工具兼容。`node tools/test_operit_prototype.cjs` 覆盖旧／重复事件、释放、两个聊天、忙碌、部位等级、关闭偏好、存储失败、发送超时、错目标结果及确认重试。

`python -m unittest discover -s tools -p test_operit_prototype_sdk.py` 使用声明安装的 MCP SDK、实际 HTTP 服务、Node HTTP 请求和隔离模拟数据库，验证 19 工具发现、模拟开始／释放、发送回调、数据库确认、另一聊天仍能查询以及会话清理。未导入旧二进制 wheel。

## 未完成与限制

用户尚未安装 Operit，尚无 APK 版本或实际 Android 连接证据。以上发送 API 为测试替身，不证明真实模型、人设效果或聊天展示。

这是同一目标单实例原型，不能把 JS 内存锁或 Android 文件读写当作多进程原子锁。手机后台与锁屏、应用强制停止、工作流执行时限、发送期间停止后的宿主取消、普通聊天与外部发送的原子排队均需真实宿主验收。发送前检查忙碌不能消除用户同一时刻发送消息的竞争。

本轮未启动真实硬件互动、未修改用户原有历史／校准，未发布 GitHub。分阶段手机验收步骤见 [操作指南](../integrations/OPERIT_PROTOTYPE.md)。

## 交付检查

提供 0.1.0 增量包及包含根目录 Python 的完整 Windows 原型包，均使用逐文件 SHA-256 清单。交付检查核对文档链接、原型启动器语法、四个预编译固件镜像与现有清单，并扫描本机配置凭据排除；不替换官方候选包和 PCB 包。

## 2026-10-15：0.1.1 Windows 启动修复

用户双击入口使用 Windows PowerShell 5.1；0.1.0 的新启动脚本是无 BOM 的 UTF-8，5.1 将其按本机 ANSI 编码解码，中文引号附近出现解析错误。此前语法检查运行在 PowerShell 7，漏掉了该兼容性问题。

修复前使用 `powershell.exe` 的解析器实际复现 5 个错误；修复后启动脚本采用带 BOM 的 UTF-8。新增 `test_operit_startup.py` 在 Windows PowerShell 5.1 中实际运行两种模式，使用含中文和空格的隔离目录及 Python 入口替身，核对参数传递。该检查验证启动器和 Python 启动，不冒充手机或真实模型验收。

打包前增加启动脚本及运行环境辅助脚本的 BOM 检查；增量和完整原型包更新为 0.1.1，保留旧包供历史核对，未替换用户配置、数据库或固件。

## 2026-10-15：0.1.2 主聊天服务检查修复

手机实际日志显示手动触发和工具分派成功，随后 `listen_interaction` 在约 17 毫秒内返回 `Chat service not connected`。该次执行尚未进入 MCP 连接；没有证据认为服务器或文件路径导致了这次错误。

核对 Operit main 的 `StandardChatManagerTool.kt`：`agentStatus` 调用 `ensureServiceConnected` 并读取绑定的 FloatingChatService；`sendMessage(runtime: main)` 则使用 MAIN core，且在发送前等待该聊天先前的活动流。旧原型把浮窗状态错误地作为主聊天发送前置条件。

0.1.2 去除该跨 runtime 检查，用 `findChat(query=chat_id, match=exact)` 验证真实已有聊天，保留 MAIN 发送和原会话模型。没有启动浮窗、创建聊天或绕过主聊天的原生等待。发送超时同时受上下文有效期和会话期限约束；新增分阶段异常，便于日志定位。

本机回归中令 `agentStatus` 始终抛出手机相同错误，原型仍能通过实际 MCP HTTP 与隔离模拟数据库完成一次发送回调及服务器确认；补充不存在聊天、原生发送仍忙碌／超时和确认恢复路径。Android 聊天接口仍是测试替身，需更新手机脚本后实际复验，不能称为已在该手机修复成功。

工作流指南补齐手动触发器和连线，并说明旧手机包需要重新导入；电脑更新不能替代手机刷新。上游依据：[聊天管理实现](https://github.com/AAswordman/Operit/blob/main/app/src/main/java/com/ai/assistance/operit/core/tools/defaultTool/standard/StandardChatManagerTool.kt)、[手动工作流接口示例](https://github.com/AAswordman/Operit/blob/main/docs/doc-src/package-dev/workflow.md)。

## 2026-10-15：0.1.3 状态路径检查

手机的新日志已进入 `delivery_state`，错误路径为 `/storage/emulated/0/Download/Operit/`：该参数指向目录，没有状态文件名。用户可以直接把参数改为 Download 下的完整 JSON 文件路径后复试 0.1.2，不必因此重启服务器。

0.1.3 增加提前检查：要求 JSON 文件名；拒绝 Files.exists 确认为目录的路径；首次创建文件前检查父目录。缺失文件仍允许首次自动生成，已有文件保持读取和恢复行为，不清空状态。新增回归覆盖截图原路径、没有后缀的目录、名为 .json 的目录与缺失父目录，核对这些错误不会创建互动会话。目录和聊天发送仍为本机测试替身，手机需单独验收。

## 2026-10-15：0.1.4 已发送回复的超时修复

手机日志显示约 16 秒后在 `main_chat_send` 返回 `Timeout waiting for AI reply`。Operit 上游该错误发生在取得回复流、等待完整回复的阶段；不能把它解释为 MCP 未连接或模型已经回复成功。

核对原型发现：发送 API 的 timeout_ms 同时被剩余会话期限裁短，15 秒短测试只给约 12 秒完成已发送模型任务。0.1.4 将会话期限用于新触摸／新发送准入，已经提交的回复等待不再被短会话立即截断，仍保留上下文剩余新鲜度上限。Operit 原生接口对队列等待与生成使用同一个 timeout，当前未宣称能将二者独立延长到任意时长。

时钟控制回归验证：15 秒会话中已提交的 20 秒回复可完成；40 秒回复仍超时并保留发送未核对状态，不能自动重发。增加用户核对后 discard 恢复，把上下文标记为用户已处理而不是模型展示成功；已有 delivered 与 not_sent 保持兼容。实际 Operit 模型是否正常、是否出现输入或部分回复仍等待用户核对，未进行真实手机慢模型验收。

## 2026-10-15：0.1.5 独立后台发送诊断

用户反馈：绑定聊天没有收到触摸回复，手动发送“你好”可回复。此结果只能确认手动聊天可用，不能证明工作流后台发送成功，也不能直接认定页面切换导致主聊天停止。上游 ChatRuntimeHolder 将主 core 放在应用级协程中，实际 APK 版本及执行行为仍需用户确认。

新增独立 `ai_doll_chat_probe` 沙盒包：只读 inspect_chat 核对原聊天标题、当前选择和近期模型元数据；send_probe 仅在用户手动工作流中发送一条可见的短自检消息，使用 MAIN 和原 ID，不连接 MCP／电脑或启动触摸会话。单独保存诊断发送状态，不覆盖或清空触摸恢复文件。

诊断分别报告 API 完整回复、编号匹配、保存历史中的输入及 AI 回复。超时仍尝试读取历史作为有限证据；不会把检查结束当作投递成功或显示成功，未知结果不自动重发。

`node tools/test_operit_chat_probe.cjs` 用明确的宿主测试替身验证可见输入、精确目标、无 MCP 依赖、只读检查、状态写入先于发送、完整回复、只有输入、没有任何历史、超时去重及存储失败。真实 Android 后台发送仍待本次手机诊断，不声称修复已在手机生效。
