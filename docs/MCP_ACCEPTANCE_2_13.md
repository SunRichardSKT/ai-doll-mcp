测试通过不自动创建平台插件、不启用物理输出。SDK 调用结果标记 `ordinary_chat_verified=false`、`sakura_verified=false`。详细编号和模拟事件只留在本机 `build/device-lab/private-mcp-device-test/`，公开报告不包含个人历史或私密地址。

Sakura 当前官方目录版本标签与文件实际版本不一致：目录标记 `0.51.0-sakura-14`，匹配目录校验值的文件执行输出 `0.51.0-sakura-15`。安装器记录两者和 `version_label_matches=false`，使用实际可执行版本请求官方配置；未忽略文件大小、MD5 或 HTTPS 校验。

2026-10-10 增加 `-ClientManaged`：复用 Sakura 客户端，只启动项目网关与监督进程，不访问 Sakura 账号 API、不保存其令牌、不启动第二个 frpc，停止项目不影响外部客户端。新增测试验证这个边界、真实连接状态要求和健康检查不覆盖实际调用证据。后续健康检查写 `remote-health-check.json`；带实际状态调用的 verify 保存在 `remote-check.json`。

复查开发板：USB 和 Wi-Fi MCP 均响应，固件 2.7.0、网络 NORMAL、模拟模式、8 个传感器通道、最多 16 个逻辑通道，物理输出关闭。采集繁忙期间的未刷新状态不能当作开发板离线；恢复后实时状态与后台同步均正常，未重刷固件。

2026-10-10 普通 Chat 新建 Sakura 连接显示“无法连接到 MCP 服务器”；同一时段电脑端 SDK 仍完成可信 HTTPS、握手、13 工具发现和两个实际状态调用。已启用私有、限量连接诊断，按重试时间核对 initialize / tools/list 及响应状态。用户随后提供完整连接地址，已确认与本机配置完全一致；Sakura 编辑页的本地地址为 127.0.0.1:8771、自动 HTTPS 开启、访问密码为空。尚未确定目标平台失败原因，也没有将其标记为安装成功。

随后用户再次创建连接仍失败。该重试时段旧版 HTTP 诊断只有固定周期的本机健康检查响应，未发现额外目标 Chat 响应；旧版仅在响应开始时写日志，不能据此认定请求未到达。电脑分别查询 Google 和 Cloudflare 公共 DNS，并对本地及公共 DNS 返回的三组 IPv4 实际执行带 SNI 的可信 TLS 与 MCP 初始化，均返回 HTTP 200；TLS 1.2 / 1.3 在电脑端均通过。直接连接及已有代理连接、HTTP/1.1 及 HTTP/2 的官方 SDK 握手和 13 个工具发现也通过。这些检查不能证明 OpenAI 云端能访问该公网入口，也不能证明是端口或节点的某项限制。完整地址已排除输入不一致；已准备新加坡节点的标准 HTTPS 表单，但没有创建新隧道或改变原隧道。

重新排查时发现并修复诊断阶段缺口：请求进入 HTTP 时立即记录，响应及未响应退出以同一编号关联；后台探测采用有限分类标记，与其他请求区分。远程 GET 改为通过地址与 Host/Origin 校验后快速返回 405，POST 继续使用 JSON。13 工具 schema 检查未发现无效或外部引用，因此不能把工具数当作已证实的失败原因。下一步在现有 Sakura 地址临时使用两个状态工具进行目标 Chat 对照，保留数据库与设备设置，成功后恢复完整配置。

首次 Cloudflare 临时转发被自动审批拒绝，理由是原计划将其安排在 ChatGPT/Sakura 验收之后，且转发可能包含设备数据或互动历史。随后用户明确允许提前进行仅两个状态工具的独立对照。已采用独立端口和随机地址，固定 `status` 配置，未转发现有 8771，也未开放互动历史。

本次修复已加载到正在运行的项目网关与监督进程。保留外部 Sakura 客户端及原完整连接地址，当前临时采用 `status` 配置。Sakura 公网可信 HTTPS 的官方 SDK 发现两个工具，实际调用两个状态工具并与服务器审计编号关联成功；ESP32 Wi-Fi 已连接、固件 2.7.0、模拟模式、物理输出关闭。经同一公网入口实测 GET 返回 405、`Allow: POST`，不再打开 SSE 流。用户再次添加 Sakura 连接仍失败；新增日志未观察到正确私密路径的未标记公网请求，不能将后台 SDK 成功标记为目标 Chat 成功。

只读复核 Sakura 客户端日志发现过数据连接超时及旧控制连接失效，随后隧道在节点 80 重新启动并加载受信任服务器证书。迁移后的 Google、Cloudflare 和本机 DNS 均指向当前节点；当前节点可信 TLS 与 MCP 初始化通过，此前节点地址已拒绝连接。这些结果不证明 OpenAI 云端使用了旧 DNS，也不能单独确定 Sakura 失败是端口、证书或节点限制。

用户授权后，独立 Cloudflare 入口启动成功，SDK 发现并实际调用两个状态工具。普通 Chat 创建连接成功，随后在北京时间 12:47:16 实际调用 `get_installation_status` 和 `doll_get_status`；两个独立调用编号、同一运行编号、对应工具名称和成功完成状态均与该入口的本机审计匹配。这是目标 Chat 的真实验收，独立于 SDK 测试。设备仍为模拟模式，物理输出关闭，设备与采集器错误均为空。

另外保存并回读了用户私有的连接代码插件。此代码插件保存与上述自定义 MCP 连接分开记录，不将上传或保存成功视为其自身已在普通 Chat 暴露工具。详细调用编号、安装地址、插件编号及来源记录留在本机 `build/device-lab/cloudflare-status-repair/`；公开包不包含这些信息。

Cloudflare 不扩大现有两工具授权范围。后续改为用户已创建的 Secure 专用隧道，固定隧道 ID，由官方客户端出站连接 OpenAI。独立本机网关提供 13 工具，设置页面、配对与数据库不作为转发目标。Windows 安装、配置、启动、停止和状态入口见 [操作指南](SECURE_MCP.md)。

Secure 初次运行出现控制服务网络超时，官方客户端的 `/readyz` 仍为成功；安装器没有据此认定远端已连通。检查发现 Windows 已启用网络代理，而原生客户端没有自动沿用系统代理。修复为仅对本项目的 OpenAI 出站连接使用电脑现有代理，回环和局域网不经过代理，不修改系统设置。之后真实轮询成功，普通 Chat 添加及调用通过。

北京时间 16:05:44 创建限时会话，数据库的结束时间恰好等于开始时间加 60 秒，结束原因为 `duration_expired`。8 条会话事件对应 4 次模拟按压，峰值原始读数分别为 3200、3200、1000、1000；未校准，不解释为真实力度。普通 Chat 返回了文字反馈，来源标明模拟；人设与偏好读取、会话开始、8 次事件续读及结束工具均有成功审计。反馈文本由用户从目标聊天提供，未将服务端事件记录当成 AI 文本生成的单独证明。

主动事件和普通 Chat 空闲唤醒仍未验证；当前结果限于用户主动发起后的执行期间。真实传感器和电机不属于此次模拟验收。详细调用编号与会话记录留在本机 `build/device-lab/secure-mcp/`，公开包只保留汇总结论。
